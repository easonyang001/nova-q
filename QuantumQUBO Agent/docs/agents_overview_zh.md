# NOVA-Q 各個 agent 在做什麼（白話版）

> 2026-10-21 整理。以墨爾本「火車站 1 公里內共享單車站巡檢路線」這題當例子。
> 每段結尾的「檔案」是對應的程式碼與提示詞，想深入時再看。

---

## 0. 一張圖看全貌

```
使用者一句話
   │
   ▼
① 需求釐清 agent ──(可上網查法規/標準)──► 「確認後的規格」        ← 人確認（實驗中用固定答案）
   │
   ├──► ② 建模模式挑選（從 18 個通用模式裡挑 ≤3 個當參考）
   ▼
③ 建模 agent ──► 模型程式（變數、目標、限制、需要哪些資料）
   │                     │
   │   ┌─────────────────┘
   │   ▼
   │  ④ 需求檢查 agent（看不到模型）──► 獨立的「裁判程式」        【關卡 G2】
   ▼
⑤ 資料偵察 agent ──► 去 10 個開放資料平台搜尋 ──► 排序、下載
   ▼
⑥ 資料處理 agent（先看資料，再寫處理計畫）──► 模型要的輸入資料   【關卡 G1：格式/單位檢查】
   │        ▲
   │        └── ⑦ 資料檢查 agent（看不到處理程式）獨立算一次「應該有幾筆」  【關卡 G3】
   ▼
⑧ 程式（非 LLM）：模型 → QUBO 編碼 → 預檢 → 求解器（SA / SQA / QAOA / QPU / CGA）
   ▼
⑨ 解答檢查（用 ④ 的裁判程式驗解答）                                  【關卡 G4】
   │   不合格 → 證據送回 ③ 或 ⑥ 修正（修復迴圈）
   ▼
交付結果
   ┊
⑩ 驗收裁判（非 LLM、事先寫死、系統看不到）只拿來評分，不參與流程   【G5，僅評估】
```

**核心想法**：「做事的 agent」和「檢查的 agent」分開、互相看不到對方的程式；
兩邊各自從使用者需求出發算一次，對不上就代表至少有一邊錯了，錯的證據送回去修。

## 1. 需求釐清 agent（Clarifier）

| 項目 | 內容 |
|---|---|
| 做什麼 | 把使用者一句模糊的話，變成一份清楚的「規格」 |
| 輸入 | 使用者的描述、之前問過的問題與回答、目標求解器的規模限制、網路查到的資料 |
| 輸出 | 規格：要決定什麼、目標、硬性限制、軟性偏好、資料範圍、假設；以及給使用者的問題（每輪最多 5 題） |
| 規則 | 只問「答案會改變問題本身」的事；其他自己決定並寫成「假設」，使用者確認時一次看過 |
| 不能做 | 決定建模方法（變數怎麼設、用什麼公式）——那是建模 agent 的事 |
| 網路 | 全系統只有它能上網，而且只查法規、標準這類外部事實；查到的每件事都要附網址 |

**墨爾本例子**：產出「巡檢 1 公里內所有單車站，每站一次、回到起點、總距離最短」。
（今天修掉的問題：它以前會把「火車站」也加成起訖點，還會把建模公式寫進規格。）

檔案：`qubo_auto/annealing/clarify.py`、`qubo_auto/prompts/annealing/clarifier.txt`

---

## 2. 建模模式挑選（pattern_pick）

| 項目 | 內容 |
|---|---|
| 做什麼 | 從知識庫 18 個「通用建模積木」（例如：選 k 個、一對一指派、巡迴路線的位置編碼）挑最多 3 個 |
| 輸出 | 被挑中的積木文字，附在建模 agent 的提示裡當參考 |
| 定位 | 只是參考，不是答案；建模 agent 可以不用 |

檔案：`qubo_auto/annealing/modeler.py`（`select_patterns`）、`knowledge/modeling_patterns.jsonl`

---

## 3. 建模 agent（Modeler）

| 項目 | 內容 |
|---|---|
| 做什麼 | 把規格寫成一個 Python 模組：二元變數、目標函數、硬性限制 |
| 必須同時寫出 | `DATA_SCHEMA`（需要哪些資料、單位、來源）、`REQUIREMENT_MAP`（每條使用者要求對應到哪些限制）、假資料產生器、`build_ir`、結果說明 |
| 規則 | 硬性限制只能放在限制清單，不能自己加懲罰項（懲罰由程式統一調）；係數用整數；變數越少越好 |
| 什麼要遵守 | 規格中的決策、目標、硬性限制名稱、數字、資料範圍、使用者回答 |
| 什麼不用遵守 | 規格中的任何公式草稿或變數寫法（今天新加的明確說明，避免它反覆糾結） |
| 失敗時 | 程式驗證不過 → 帶著錯誤訊息重寫，最多 4 次 |

**墨爾本例子**：用「第 t 個位置去第 i 站」的位置編碼，n 站就是 n² 個變數。

檔案：`qubo_auto/annealing/modeler.py`、`qubo_auto/prompts/annealing/modeler.txt`

---

## 4. 需求檢查 agent（Requirement Checker）——關卡 G2

| 項目 | 內容 |
|---|---|
| 做什麼 | 只看規格和資料格式，**看不到模型**，自己寫一支「裁判程式」：給一組決策，判斷合不合規、算目標值；另外能隨機產生合規的解 |
| 怎麼用（解之前） | ① 隨機合規解丟進模型，模型必須也說合規；② 模型的目標排名要和裁判一致；③ 把合規解故意改壞一點（少一站、多一站），模型必須說不合規——抓「把『剛好 5 個』寫成『最多 200 個』」這類放水 |
| 怎麼用（解之後） | 交付的解必須通過裁判程式（關卡 G4） |
| 意義 | 對不上只是「證據」，不是判決；裁判也可能錯，所以證據送回建模 agent 判斷 |

檔案：`qubo_auto/annealing/reqcheck.py`、`qubo_auto/prompts/annealing/req_checker.txt`

---

## 5. 資料偵察 agent（Scout）＋ 候選排序

| 項目 | 內容 |
|---|---|
| 做什麼 | 根據模型需要的資料，提出搜尋關鍵字；**實際搜尋和下載是程式做的**，它不能編網址 |
| 搜尋來源 | data.gov.tw、OpenStreetMap、國外開放資料平台（CKAN、Socrata、Opendatasoft、ArcGIS、歐盟、英國 Nomis 等）、出版單位網頁 |
| 排序 | 第二次呼叫 LLM 看每個候選檔的欄位預覽，排出最相關的；官方資料優先於 OSM 群眾資料；同一資料集多年份只留最新 |
| 失敗時 | 下載失敗就換下一個候選；搜不到就換關鍵字（最多 2 輪、4 個檔） |

**墨爾本例子**：找到墨爾本市政府的 `Bike_Share_Dock_Locations` CSV。

檔案：`qubo_auto/annealing/opendata.py`、`qubo_auto/prompts/annealing/scout.txt`

---

## 6. 資料處理 agent（Data Agent / Adapter）——關卡 G1 的一部分

| 項目 | 內容 |
|---|---|
| 做什麼 | 把下載的原始表格整理成模型要的格式 |
| 怎麼做 | **先看、後做**：每回合只能做一件事——用唯讀工具看資料（欄位、某欄有哪些值、幾列樣本、兩表的鍵能不能對上、哪個代碼在哪個區），或交出一份「處理計畫」 |
| 處理計畫 | 不是自由寫程式，而是從 19 種測過的工具挑步驟排順序：只留最新期別、只留總計列、依真實行政區界篩選、半徑篩選、合併同一地點、座標轉換、合併表格…… |
| 檢查 | 計畫先在完整資料上試跑；輸出的鍵、筆數、單位、期別、地區要和模型宣告的一致（關卡 G1） |
| 硬規則 | 公開資料缺的值絕不能補預設值（例如人口全填 1）→ 要回報「資料缺口」讓系統再去找；不能拿別種東西頂替（例如拿捷運出口當單車站） |
| 失敗時 | 計畫模式試 2 次（每次最多 10 步），不行再改寫 Python；再不行，證據送回建模 agent 改模型（最多 1 次） |

**墨爾本例子**：看欄位 → 依火車站座標做 1 公里半徑篩選 → 合併同一地點 → 算距離矩陣。

檔案：`qubo_auto/annealing/dataagent.py`、`adapter.py`、`dataplan.py`、`prep.py`、
`qubo_auto/prompts/annealing/adapter_plan.txt`、`adapter.txt`

## 7. 資料檢查 agent（Data Checker）——關卡 G3

| 項目 | 內容 |
|---|---|
| 做什麼 | 只看規格和原始表格摘要，**看不到資料處理 agent 的程式**，自己獨立算：篩選後每個集合應該有幾筆、每個數值欄加總應該多少 |
| 比對 | 和資料處理 agent 的輸出比；不一致就把證據送回去重做 |
| 抓到的錯誤類型 | 區域篩錯、類別沒排除、期別混在一起、同一地點重複計算 |

檔案：`qubo_auto/annealing/datacheck.py`、`qubo_auto/prompts/annealing/data_checker.txt`

## 8. 程式部分（不是 LLM）

| 步驟 | 做什麼 |
|---|---|
| QUBO 編碼 | 把模型的限制自動轉成懲罰項（含 slack 變數），統一調懲罰權重 |
| 預檢 | 檢查規模能不能放進求解器、找一個簡單可行解當基準 |
| 求解 | 實驗主線用 SA；海報比較用 SQA、CUDA-Q QAOA、D-Wave QPU、CGA。每次最多 3 次求解呼叫 |
| 交換修整 | 解出來後用「保持合規的局部交換」再改善一點 |
| 修復迴圈 | 解不合規或品質差 → 依證據送回資料處理或建模（最多 2 次）；**修復不能改使用者設定、不能刪限制、不能改目標方向**，否則保留舊版本 |

檔案：`qubo_auto/annealing/workflow.py`、`assessment.py`、`repair.py`、`backends.py`

---

## 9. 驗收裁判（Judge）——G5，只用來評分

| 項目 | 內容 |
|---|---|
| 是誰 | 一支**事先寫好、凍結**的 Python 程式，不是 LLM；系統在跑的時候看不到它 |
| 標準答案 | 從原始官方檔案直接算出的「真值」（例如墨爾本：火車站 1 公里內 11 個站） |
| 三項判定 | **資料**：每個實體對得上真實實體、沒漏沒重複、數值正確；**模型**：隨機合規解的排名和真實指標一致、違規解被判不合規；**交付**：解合規，且品質和簡單參考解差距 ≤ 10% |
| 用途 | 海報表格裡的「x/3 通過」就是它判的 |

檔案：`acceptance/judge.py`、`acceptance/truth.py`、`acceptance/cases.json`

## 10. 誰看得到誰（獨立性）

| 做事的 | 檢查的 | 檢查者看不到 |
|---|---|---|
| 建模 agent | 需求檢查 agent | 模型程式 |
| 資料處理 agent | 資料檢查 agent | 處理程式 |
| 整個系統 | 驗收裁判 | ——（反過來，系統看不到裁判） |

實驗中做事與檢查都可以設成不同模型家族（海報上的 cross-family 98% vs same-family 73%）。
目前墨爾本這批：兩張 L40S 各跑一個 Gemma-4-31B，每張卡上做事與檢查用同一個 Gemma。

## 12. 2026-10-21 修掉的互相矛盾（為什麼 Gemma 會想不完）

| 位置 | 原本的矛盾 | 現在 |
|---|---|---|
| 需求釐清 | 一邊說「不要寫建模技巧」，一邊要求寫變數、公式、輔助變數數量 | 只用白話描述決策與要求 |
| 需求釐清 | 「技術方法自己決定並寫成假設」→ 使用者一確認就變成必須遵守 | 技術方法不寫進規格 |
| 需求釐清 | 把只用來劃範圍的火車站加成起訖點 | 地標不是站點，除非使用者說要 |
| 建模 | 「忠於規格」vs「建模方式你自己決定」，規格裡又有別的公式 → 反覆對照到逾時 | 明講哪些要遵守、哪些只是參考 |
| 建模修正 | 只能修實作，不能換建模方式 | 可以換方式，不能改需求 |
| 需求檢查 | 可能去檢查規格裡的公式草稿 | 只檢查需求 |
| 資料處理 | 「可以合併到行政區」vs「每個 id 都要保留」 | 只能依資料範圍篩選 |
| 資料處理 | 要求輸出 JSON，結尾卻叫它寫 Python 變數 | 依模式分開講 |
| 資料探索 | 「直接回傳計畫」vs「先看資料」→ 不看就交 | 講清楚要先看再交 |

## 13. 實驗設定（墨爾本 v7，今天 17:00 UTC 起）

- 模型：Gemma-4-31B-it FP8（兩張 L40S 各一個，context 160k）
- 每次 LLM 呼叫最多 20 分鐘；逾時就關掉「思考」再答一次
- 資料處理用「先看再做」模式，求解器 SA
- 停止規則：先完成的 3 次算 x/3；凌晨 3 點前墨爾本 0 通過就改跑 Basel AED 分組題
