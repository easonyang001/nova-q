# 實驗計畫（2026-10-12 版）

本文件規定論文所有實驗的設計、題目、指標、統計與執行順序。主實驗的分析細節以 `acceptance/PREREGISTRATION.md` 為準；兩者衝突時以事先登記文件為準。

## 0. 論文主張與對應的實驗

| 主張 | 對應實驗 | 成立的條件 |
|---|---|---|
| C1：完整系統比直接用 LLM 更常交付符合需求的方案 | E1（開發集）＋ E1-T（測試集） | 測試集上 R3 的交付率高於 R0，且每題結果方向一致 |
| C2：每個機制各有貢獻，成本可接受 | E1 的機制階梯 R0→R3、E3、E7 | 每一階的增益與成本分開報告，不要求每一階都顯著 |
| C3：各層驗證能抓到不同類型的錯，而且很少誤報 | E2（＋ E6） | 每層抓錯率、誤報率附信賴區間；各層抓到的錯誤類型互補 |
| C4：開放世界的資料取得是主要瓶頸，目錄檢索能改善 | E5 | 資料存在的項目中，找到率提高 |
| C5（輔助）：penalty 調整的價值隨問題規模改變 | E4 | 分規模報告，不做一般性宣稱 |
| C6（輔助）：資料給定時，建模與驗證段的可靠度 | E8 | 和端到端結果對照，分出兩段各自的失敗比例 |
| C7（輔助）：退火機在實際交付中的角色 | E9 | 和 MILP、模擬退火、簡單基準並列報告，不宣稱量子優勢 |
| 穩健性 | E10、敏感度分析、判定稽核 | 主結論在不同措辭與門檻下不改變 |

不主張：系統能可靠處理任意題目；開發集的成績代表泛化能力。

## 1. 版本鎖定與開跑條件

1. **開發收尾**：最後一輪開發驗證（10 題）之後，只允許修正基礎設施錯誤，例如程式崩潰；不再為了個別題目修改程式或提示詞。
2. **鎖定內容**：程式、提示詞、知識庫、求解設定、判定程式、題目設定、標準答案的 SHA256 寫入 manifest；資料目錄另外記錄每個入口網站的筆數與建立日期。
3. **開跑條件**（`scripts/preflight.py` 全部通過）：
   - 單元測試與判定程式自我測試通過；
   - 本機 LLM 可連線；CGA 可連線，且剩餘呼叫額度大於 2000；
   - 硬碟空間足夠；沒有其他實驗在跑；
   - 最後一輪開發驗證**至少 5/10 題交付，且至少 1 題國際題**。
4. 未達第 3 點最後一項時，不開主實驗，改為在論文中報告開發集的失敗分析。這個決定事先寫在這裡，不事後改。

| 集合 | 用途 | 內容 | 狀態 |

- 國家和開發集不同；
- 至少一種開發集沒有的問題結構；
- 官方資料可以公開下載；
- 標準答案可以用精確 MILP 或明確的參考解算出；
- 每題有大小兩版。

## 3. 實驗設計

### E1 主實驗：端到端機制階梯（開發集）
- **組別**：R0 `direct`、R1 `pipeline`、R2 `no_repair`、R3 `full`、R3＋RAG `full_rag`、R3−上網 `full_noweb`（定義見事先登記文件第 2 節）。
- **重複**：每題 3 次。共 10 題 × 6 組 × 3 次 = **180 次**。
- **執行順序**：先以固定種子打亂（題目, 組別, 次）的順序，再交錯執行，避免時間漂移（網路、即時資料、伺服器負載）集中影響某一組。
- **指標**：找到資料、資料正確、模型正確、可用交付（退火機解與基準解分開）、token、時間、求解次數、人工介入次數。全部由獨立驗收判定。
- **統計**：以題目為區組的 Cochran–Mantel–Haenszel 精確檢定（單尾）、Holm 校正。主要報告每題成功次數與比例，並附 Wilson 95% 信賴區間。
- **預估成本**：每次約 10–25 分鐘；同時跑 2 個時約需 25–35 小時；CGA 最多 540 次呼叫。

### E1-T 測試集
- **組別**：R0 與 R3＋RAG（主假設 H1 的兩端）；時間允許時加 R1。
- **重複**：每題 3 次。共 10 題 × 2 組 × 3 次 = **60 次**。
- 第一次執行就是正式結果，不除錯、不重跑，基礎設施故障除外。

### E2 故障注入：各層驗證抓得到什麼
- **種子**：鎖定後在開發集上完整通過的執行結果，每種問題結構至少 1 個。
- **故障清單**（事先固定）：

| 代號 | 故障 | 層面 |
|---|---|---|
| D1 | 少了約 10% 實體 | 資料 |
| D2 | 同一地點以兩個 ID 出現 | 資料 |
| D3 | 3 個實體經緯度對調 | 資料 |
| D4 | 3 個量測值放大 10 倍 | 資料 |
| D5 | 混入一列上層合計（例如「總計」） | 資料 |
| D6 | 混入範圍外的實體（鄰近行政區） | 資料 |
| M1 | 刪掉一整組限制式 | 模型 |
| M2 | 目標函數正負號顛倒 | 模型 |
| M3 | 刪掉所有二次項（重疊只算一次失效） | 模型 |
| M4 | 數量限制差 1 | 模型 |
| M5 | 某實體的變數被移除（固定決策） | 模型 |
| M6 | 目標函數權重用錯欄位 | 模型 |

- **檢查層**：L1 資料格式與契約；L2 需求檢查（Checker）；L3 資料交叉核對；J 獨立判定（標準答案，用來判斷故障是否真的有害）。
- **LLM 產生的檢查程式**（L2、L3）每個種子各建立 3 次，報告平均值與範圍。
- **指標**：
  - 對有害故障：每層的抓錯率，以及多層合計的抓錯率；
  - 對無故障的種子：每層的誤報率；
  - 附 Wilson 信賴區間。

### E3 跨階段修復的消融
- **自然發生的失敗**：比較 E1 中的 R2 與 R3，對每個失敗，看修復是否把它救回來，記錄修復成功率與額外成本。
- **控制注入**：在 E2 的種子上注入 D1–D6、M1–M6 的故障，讓 R3 從被注入的階段繼續執行，量測修復後能否達到可用交付。這可以分開回答「偵測到了，能不能修」。

### E4 規模分層的 penalty 調整（輔助）
- **規模**：約 100、300、500、1000、1500、2000 個變數（YouBike 路線題，調整站點數）。
- **方法**：預設 penalty、逐步調整、TPE、單代理、多代理。
- **重複**：真實硬體（CGA）每個條件跑 1 次；本機模擬退火每個條件跑 3 次，報告平均與範圍。
- **指標**：可行率、與 MILP 參考解的差距、求解次數。

### E5 資料取得：目錄檢索的效果
- **集合**：資料壓力集 100 筆。
- **組別**：關鍵字搜尋（舊）與目錄檢索＋關鍵字（新）。資料目錄在執行前凍結。
- **資料存在性**：**這次在執行前**逐筆確認每筆需求的資料是否存在，寫入固定的表格；只有「不存在或沒有需求的形式」的項目從調整後的分母排除。原始比例與調整後比例都報告。
- **指標**：找到率、資料整理成功率，以及每個階段的失敗類型。

### E6 檢查模型多樣性
- **組別**：檢查角色（L2、L3）使用和執行者相同的模型（Qwen3.6-35B-A3B），或不同家族的模型（Gemma 4 31B）。
- **量測**：E2 的抓錯率與誤報率；時間允許時，加一輪開發集 R3＋RAG 的交付率。
- **GPU**：第二個模型放在 GPU 1，**只在這個實驗執行期間開啟**。

### E7 前處理模式
- **組別**：資料計畫（工具執行，失敗時才退回自由程式）與自由程式（`QUBO_ADAPTER_MODE=code`）。
- **量測**：開發集 R3＋RAG 每題 1 次的資料正確率，以及資料計畫獨自完成的比例。

### E8 給定正確資料（拆開資料段與建模段）
- **設定**：跳過資料取得與前處理，直接把標準答案使用的資料（集合＋參數格式）交給系統，只跑建模 → 驗證 → 求解 → 交付。
- **組別**：R0（直接 LLM，資料給定）與 R3＋RAG；每題 3 次。
- **用途**：
  - 把端到端的失敗拆成「資料段」和「建模段」；
  - 和資料給定的相關研究（ORLM、OptiMUS、ORAgentBench）在相近條件下比較。

### E9 求解器比較
- **設定**：對 E1 中模型判定正確的每個 QUBO，分別用 CGA（預設 penalty）、本機模擬退火、HiGHS（原始限制式的 MILP）、系統內建的簡單基準各求解一次。
- **指標**：
  - 和最佳已知解的差距；
  - 可行率；
  - 實際花費時間（CGA 另外列出排隊和傳輸的開銷）。
- **用途**：說明退火機在這類問題上的實際價值與限制，不做「量子優勢」的宣稱。

### E10 使用者回答的穩定性
- **設定**：每題準備 3 種措辭不同、意思相同的固定回答（事先寫好，鎖定後不改），用 R3＋RAG 各跑 1 次。
- **指標**：
  - 釐清出的規格是否一致（硬性需求是否相同、資料範圍規則是否相同）；
  - 交付結果是否一致。

## 4. 判定與指標

- 判定規則見 `acceptance/README.md` 與事先登記文件第 4 節：
  - 資料：一對一實體、量測值、總數；
  - 模型：30 組方案的排序一致性，以及違規方案被拒絕；
  - 交付：符合需求，且和參考解差距在 10% 以內。
- 「無法驗證」在主分析中算作不正確，另附排除它們的敏感度分析。
- 判定程式在鎖定後只能修正**崩潰類**錯誤；任何修改都要記錄，而且對所有已完成的執行重新判定。

### 判定程式稽核
- 從 E1 隨機抽 20 次執行，成功與失敗各 10 次。由人工根據原始資料逐項確認資料、模型、交付三項判定；最好由第二人獨立確認。
- 報告判定程式與人工的一致率；不一致的個案逐一說明。

### 失敗原因分類
- 事先固定的類別：
  - 搜尋（沒有找到可用資料）；
  - 下載／讀取；
  - 前處理（實體、範圍、數值錯誤）；
  - 建模（無法建立或結構錯誤）；
  - 需求不符（模型和需求不一致）；
  - 求解（不可行或品質不足）；
  - 交付（最後的方案不符合需求）。
- 每個失敗只歸到**最早**出錯的階段。兩人各自分類，報告 Cohen's κ，不一致的協商後定案。

### 敏感度分析
- 交付差距門檻另外用 5% 與 20% 重算；排序相關門檻另外用 0.8 與 0.95 重算；「無法驗證」排除後重算。
- 報告主結論（H1）在這些設定下是否改變。

### 可重現性
- 公開：程式、提示詞、知識庫、manifest、資料目錄快照（入口網站、筆數、日期）、所有 LLM 對話紀錄、標準答案、判定程式與自我測試。
- 即時資料題附上每次執行實際下載的檔案。

## 5. 對效度的威脅與對策

| 威脅 | 對策 |
|---|---|
| 開發集被過度調整 | 測試集鎖定後才建立、只跑一次；論文清楚區分兩者 |
| 判定程式是看過試跑後修改的 | 修改紀錄公開（事先登記文件第 9 節）；每次修改都用自我測試確認仍能抓到故意做錯的輸出；另外人工抽查 20 個判定 |
| LLM 結果的隨機性 | 每題 3 次；溫度 0；報告每題的次數，不只報告平均 |
| 即時資料變動 | 用系統自己下載的檔案重算標準答案；沒有官方檔案的，記錄時間差 |
| 檢查和被檢查的是同一個模型 | E6 |
| 只有一個本機模型 | 論文明確限定範圍；時間允許時加前沿模型的對照組（需要 API key） |
| 資料存在性的事後判定 | E5 改為執行前判定 |
