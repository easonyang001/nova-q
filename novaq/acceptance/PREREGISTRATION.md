# 事先登記的分析計畫

狀態：**主假設與判定規則已確認（2026-10-12，使用者同意採用建議版本）；題目清單中的測試集待確認。**
程式鎖定後，一律依照本文件分析，跑的過程中不修改。

## 1. 研究問題
- **RQ1**：完整系統（R3）比直接 LLM（R0）更常交付符合原始需求的方案嗎？
- **RQ2**：每一個機制各帶來多少可靠度、各花多少成本？
  - R0→R1：流程與工具；
  - R1→R2：需求驗證；
  - R2→R3：跨階段修復；
  - R3→R3＋RAG：建模模式檢索；
  - R3→R3−上網：Clarifier 上網查證。
- **RQ3**：驗證機制能抓到哪些錯誤、誤報多少？另外用故障注入實驗（E2）回答，不在本批。

## 2. 設定（變因）
| 組 | 內容 |
|---|---|
| R0 `direct` | 直接 LLM，自己上網找資料，只有 Python 錯誤回饋 |
| R1 `pipeline` | Clarifier、集合＋參數格式、資料目錄檢索與平台連接器、資料計畫（工具執行）、資料契約 |
| R2 `no_repair` | R1 ＋ 需求 Checker ＋ 資料雙重計算（只偵測，不修） |
| R3 `full` | R2 ＋ 跨階段修復 |
| R3＋RAG `full_rag` | R3 ＋ 建模模式檢索 |
| R3−上網 `full_noweb` | R3，關閉 Clarifier 上網 |

**固定不變的條件**：
- LLM：Qwen3.6-35B-A3B-FP8，溫度 0，本機 vLLM；
- 求解：CGA，預設 penalty，最多 3 次；
- 各階段重試次數：見 `cases.json` 的 `budget`；
- 資料目錄（`results/data_cache/catalog/`）在鎖定時凍結，記錄每個入口網站的筆數與建立日期。

## 3. 題目
**開發集**（已用來除錯，10 題）：台北充電站、YouBike 巡檢、AED 分組、倫敦救護站、柏林遊戲場，各有小版與大版（見 `cases.json` 與 `README.md`）。

**測試集**：開發集定案、程式**再次鎖定**之後才建立標準答案並第一次執行；期間不為它修改任何程式。
候選（待使用者確認）：紐約冷卻中心（最大覆蓋）、巴黎 Vélib' 巡檢（路線）、阿姆斯特丹衛生站（p-median）、
新加坡小販中心分組（平衡分組）、多倫多消防站（集合覆蓋，開發集沒有的結構），各有小版與大版。

## 4. 每次執行的指標（全部由獨立驗收判定）
1. **找到資料**：這次執行自己取得至少一份可讀的資料檔。
2. **資料正確**：實體一對一對上真實資料，沒有遺失、重複或捏造；座標正確；量測值逐一相符；總數正確。
3. **模型正確**：
   - 30 組符合需求的方案在模型裡都可行，而且排序和真實指標一致（Spearman ≥ 0.9）；
   - 違反需求的方案被判為不可行。
   - 「**無法驗證**」在主分析中**算作不正確**，另附排除它們的敏感度分析。（已確認）
4. **可用交付**：交付的解符合原始需求，而且真實品質不比原始資料上的參考解差超過 **10%**。（已確認）
   - 方案來源不論是退火機或簡單基準都算交付，但**分開報告**。（已確認）

## 5. 成本
- LLM token 數、實際花費時間、求解次數；
- **人工介入次數**，逐項計數：
  - 回答 Clarifier 的輪數；
  - 確認規格（1 次）；
  - 核准資料（1 次；批次中自動核准，核准得對不對由驗收判定）；
  - 使用者提供資料連結或檔案的次數（批次中為 0；之後的「人在迴圈中」實驗另外報告）。
- 前處理以資料計畫完成或退回自由程式完成，各占多少。

## 6. 假設與統計
- **H1（主假設）**：R3 的可用交付率高於 R0。（已確認）
- **H2**：R1 的資料正確率高於 R0。
- **H3**：R2、R3 的模型正確率高於 R1。
- **H4**：R3＋RAG 的模型正確率高於 R3。

**統計方法**：
- 每題 3 次，所以每組總樣本數 ＝ 題數 × 3；
- 以題目為區組做配對比較：Cochran–Mantel–Haenszel 精確檢定，單尾；
- 多重比較用 Holm 校正；
- 樣本少，**主要報告每題的成功次數和整體比例**，p 值只作輔助，不宣稱很強的顯著性。

## 7. 排除和重跑規則（已確認）
- **只有基礎設施故障可以重跑一次**，並記錄原因：vLLM 停止服務、網路中斷、CGA 服務無法連線。
- **以下都算系統本身的結果，不重跑**：LLM 逾時、模型輸出錯誤、找不到資料、下載的資料格式不對。
- **即時資料**：判定時以系統自己下載的官方檔案重算標準答案；沒有用官方檔案的，用事先下載的快照判定，並記錄時間差。
- **資料存在性**（只用於資料壓力測試，不用於主實驗）：搜尋失敗的項目，事後逐項確認公開資料是否存在；
  確認「不存在或沒有需求的形式」的才從調整後分母排除，原始比例與調整後比例都報告。主實驗的題目都已有官方標準答案，資料一定存在，不排除。

## 8. 鎖定
manifest 記錄下列項目的 SHA256，任何一項改變就拒絕繼續：程式、prompt、知識庫、求解設定、判定程式、題目設定、標準答案。
資料目錄另外記錄筆數與建立日期。

## 9. 已知限制，事先聲明
- 建模知識庫、資料目錄的評估需求清單，是在看過試跑之後寫的。
- 判定程式在看過試跑之後修正過，每次都是放寬了**不該失敗的**誤判，並以自我測試確認仍能抓到故意做錯的輸出：
  - 名稱比對先於座標比對（山區里的中心點離官方點位遠）；
  - 人口表代碼與界圖代碼（CPTVID）都接受；
  - ID 分隔符號正規化；路線允許任意起點與反向；
  - 資料錯誤時，分區類題目判為「無法驗證」而非「錯」；
  - 交付檢查涵蓋所有真實實體；
  - 接受前面帶城市名的里 ID（「臺北市南港區舊莊里」）。
- 開發集的結果**不能**當作泛化能力的證據，泛化能力由測試集回答。
- 資料壓力測試的資料存在性確認，是開發者在執行後做的。
